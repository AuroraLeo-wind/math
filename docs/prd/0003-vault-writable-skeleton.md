# PRD-0003 · Obsidian 知识库落地：vault 化、可写骨架与标题修复（M0–M4）

> 依据：2026-11-06「grill 十问」结论（落点为 `CONTEXT.md` 重写、ADR-0004、ADR-0005、ADR-0002「后续修订」、ADR-0003「增补」）。
> 领域词汇以 `CONTEXT.md` 为准；架构与技术栈以 `docs/adr/` 为准，本 PRD 只摘要与本功能相关的结论。
> **UI 模式：headless** — 产品形态是 Obsidian vault（Markdown）+ 命令行脚本；Obsidian 是第三方渲染/编辑面，本仓库不自建任何 UI。因此省略「UI 与设计要求」整章，也不写状态策略（ADR-0003 增补「渲染与编辑面」）。
> 与 PRD-0002 的关系：本 PRD 接管其 **vault 落地** 部分，并把「三路召回检索服务」整段移出范围（降期为里程碑 M5）。PRD-0002 的 vault 契约、输出分区、引用纪律仍然有效，只是不再属于本期交付。

---

## 问题陈述

使用者（单人、考研数学、已在用 Obsidian）当前卡在六件事上：

1. **数据改不动。** 2375 张证据卡、1748 个骨架节点都在 JSONL 里，改一个标题要手写 JSON。而实测 **1343/2375 张卡的标题是正文句子**（全部因超过 24 字被判「标题可疑」），其中 `method` 卡 245 张——AI 回答时会把它们当方法名念出来，这是引用可信度的最大风险项。
2. **结构长不出自己的东西。** 骨架是 KK 原图的重建物、只读。使用者要的是「形成自己总结与导图思想匹配的新结点插入导图中」——在 KK 的分类法上长出自己的分类；现状只能把总结写成卡，永远挂在 KK 节点下面。
3. **挂载精度是假象。** ADR-0001 记录覆盖 75%（1789/2375）；当前数据看起来 2374/2375 都有挂载，但其中 **914 张（38.5%）的章名与骨架对不上**，被「同科目全库兜底」硬挂到某个节点上——数字好看了，精度没有。这批卡会把结论挂到错误的分类上。
4. **张宇那套方法论层缺着。** 张宇 8 本共 2085 页，其中 7 本无文本层（0–1.5 字/页），只有 1000 题试题册 195 页可直接抽；而缺的正是「这一类题怎么想」的方法细节。
5. **手改会被下一次导出冲掉。** 现有导出脚本每次全量重写，使用者无法知道哪次重跑会覆盖掉一周的整理。
6. **没有整理入口。** 1343 条待修标题、1186 个空壳节点（其中 940 个非噪声，另 269 个是「进阶练习/视频链接」类噪声节点）、一堆挂不上的卡——「该修 / 该审 / 该补」三件事全散落在脚本输出里，人没有地方干活。

一句话：**数据在，但没有一处是「人能直接整理、AI 能直接读、重跑不会毁掉」的形态。**

## 解决方案

把知识库并入使用者**现有** Obsidian 库的专属子目录，让它成为唯一权威来源（SSOT）；导出**默认增量**；把人的整理动作收敛成「工作台（静态清单）→ 勾选 → 回灌」这一个循环；骨架**可增**（用户节点 + 提议机制）；张宇方法论层用**后台 OCR** 补齐；视图（mermaid 章级）是只读派生物。

```
D:\文档\Obsidian Vault\考研数学\        ← 知识库前缀，脚本只写这里；库内 C++ 笔记只读不碰
├── 00-工作台/                          静态清单页（脚本生成，可 diff、AI 可读）
│   ├── 待修标题-方法卡.md   ← 245 条（带「建议标题」列）
│   ├── 待修标题-例题卡.md   ← 规则改不动的残余
│   ├── 待审提议.md          ← 提议索引（链到 04-待整理/）
│   ├── 空壳节点.md          ← 无卡无笔记的骨架节点
│   └── README.md            ← 三件事怎么做、回灌命令
├── 01-骨架/<章>.md                    每章一个 MOC：mermaid 视图 + 节点 heading 树 + 该节点的卡链接
├── 02-证据卡/<类型>/<id>-<标题>.md     一卡一文件，frontmatter 是结构化字段
├── 03-笔记/                           使用者自由写的 Markdown，用 anchors 挂到节点
├── 04-待整理/提议-<id>.md             一条提议一页，勾选「采纳 / 合并到 X / 丢弃」
└── .backup/<时间戳>/                   全量重建前的自动备份（库内可见、不进检索）
```

五条交付主线（里程碑与验收线见「补充说明」）：

| 主线 | 内容 | 里程碑 |
| --- | --- | --- |
| 后台 OCR 张宇 | 18 讲 309 页 + 9 讲 97 页 = 406 页；1000 题试题册直接抽文本层 | M0 → M4 合流 |
| vault 化 | 骨架 → 章 MOC（含 mermaid）、卡 → 一卡一文件、工作台四页 | M1 |
| 修标题 | 规则批量重写 + 方法卡人工（带建议标题）+ 勾选回灌 | M2 |
| 自己的节点 | 章名别名表 → 提议 → 勾选采纳 → 用户节点入树 | M3 |
| 增量与回灌 | 增量导出、`--force` 前自动备份、vault → 结构化数据回灌 | 贯穿 M1–M4 |

**成功判据不是「导出成功」，而是「改得动、长得出、补得进、冲不坏、数得清」。**

## 实现决策

### vault 目录契约与写入前缀

唯一权威来源是 `D:\文档\Obsidian Vault\考研数学\`；库内其它内容（27 篇 C++ / 后端笔记）只读不碰，脚本的**所有**写入路径硬编码该前缀（`知识库前缀`）。目录固定为 `00-工作台/`、`01-骨架/`、`02-证据卡/<类型>/`、`03-笔记/`、`04-待整理/`、`.backup/`。

- 卡按 `kind` 分五个子目录：方法卡 / 例题卡 / 症状卡 / 陷阱卡 / 结构卡。
- `.backup/` 在库内可见（便于人工回滚），但不进检索扫描范围、不参与导出统计。
- `03-笔记/` 由使用者独占写入，脚本只读不写。
- 现有 `export_obsidian.py` 只产出「MOC + 一卡一文件 + README」，本 PRD 要求新增 mermaid 视图、工作台四页、增量与备份、`origin: user` 支持——这是改造而不是新建。

### 增量导出与 --force 备份

导出默认**增量**：只写「库里不存在」的文件，已存在的一律跳过，不对比内容、不做字段合并。

- 全量重建必须显式 `--force`；执行前自动备份到 `考研数学/.backup/<时间戳>/`，打印「将覆盖 N 个已存在文件，已备份到 …」，并要求输入 `yes`。
- 卡 frontmatter 的 `edited: true` 只作兜底（字段级线索），**不作**主策略——主策略是「默认不动」。
- 推论（写进文档，避免误解）：抽取算法改进后，旧卡的错误标题不会被自动修好；那本来就要人工改写，属于同一个动作。

### 卡片文件契约

文件名 `{卡id}-{标题截断 22 字}`，非法字符（`\ / : * ? " < > | # ^ [ ]`）替换为 `-`，重名追加 `-2`；**卡 id 是文件身份**，回灌与增量判定都按 id 匹配、不依赖文件名。

frontmatter 必含：`id / kind / subject / chapter / topic / title / source_file / source_page / source_page_end / anchor_score / confidence / kk_anchor / title_suspect / exported_at / export_version`，可选 `edited`；`tags` 至少含 `考研数学` 与科目、类型。

正文结构：`# 标题` → 「类型 / 出处 / 归属骨架（`[[节点]]`）」要点行 → 分节（识别信号 / 适用条件 / 失效边界 / 方法链 / 关键公式 / 陷阱 / 变式 / 原文，按字段存在与否渲染）。

标题变更时由脚本负责**重命名**文件（按 id 找到旧文件 → 改名），不要求人手工改文件名。

### MOC 页结构与视图

每 `(科目, 章)` 一个 MOC 文件（实测 39 章、43 本导图按 slug 分节）：

1. frontmatter（`chapter / subject / nodes / cards / tags`）；
2. 顶部一行统计（节点数 / 卡数 / 版本数）；
3. **mermaid 视图**：`mindmap` 渲染该章骨架；仅画主版本；节点数 > 150 的章只画 `depth ≤ 3`，其余节点进工作台「展开清单」，全树另开 markmap 页；同名章的「自测版本」折叠进 `<details>`，不进图；
4. 节点 heading 树（层级 = 骨架 depth），每个节点后标注 `(N卡)` 或 `0卡`，其下挂该节点的卡 `[[文件名]]`；
5. 章末「0 卡节点」巡检清单。

`exercise_hint: true` 的 269 个噪声节点**不进** heading 树、不进 mermaid、不进「空壳节点」清单（它们是「进阶练习/视频链接」类占位）。

### 用户节点 schema

用户节点与 KK 原生节点同一棵树共存，额外字段只有三个：

- `origin: "user"`（缺省视为原生节点）；
- `summary`：一行说明「这个节点管什么」，**必填**，≤40 字；
- `parent`：挂靠的父节点（沿用既有字段，不允许为空——用户节点不能是书名根）。

沿用既有 `node_id / path / depth / column / subject / chapter / children`；**不带** `bbox`（不在 KK 原图上）；`slug` 继承父节点所属书，以便章 MOC 仍能按书分节。`content`（可选正文）只允许写自己的话，禁止抄课件原文，要引原文写成 `[[卡文件]]` 链接；长结论仍落成证据卡，不写进节点。

### 用户节点渲染与辨识

MOC 里用户节点的 heading 文本追加后缀 `（我的）`；mermaid 里同一节点带 `:::user` 类，并尝试 `classDef user` 虚线描边（`stroke-dasharray`）。**渲染器不支持 mindmap 的 classDef 时以文本后缀为准**——验收断言落在文件层面（后缀存在），不依赖渲染器的视觉能力。

### 提议生成

提议文件 `kb/proposals.jsonl`，每条 `{proposal_id, proposed_node, summary_hint, parent_path, evidence_cards[], kind, reason}`；对应库内 `04-待整理/提议-<id>.md` 一页。

候选与门槛：

1. **前置**：先去落地「章名别名表」（见下），再算候选——否则提议会变成给映射缺陷打补丁。
2. 候选 = 别名表落地后仍**无同章可挂节点**的卡，按 `(章 + 题型)` 聚簇；
3. 只对两类发起提议：① `kind=method` 且标题可读（中文字符占比 ≥60%、长度 ≤24 字、非标题可疑）；② 同章同题型 **≥3 张**的 `example` 卡簇（提议一个题型级节点，落 `题型结构化` 栏）；
4. 实测基线（当前数据）：章名对不上的卡 914 张，其中可读短标题 323 张（`method` 46 张、`example` 267 张）；`(章, 题型, kind)` 聚簇 ≥3 张的有 39 簇 / 272 张卡。别名表落地后这些数字会下降，可再测。
5. 提议**只增不改**：已有 KK 节点永不被提议改名或删除。

### 提议回灌（勾选即生效）

`04-待整理/提议-<id>.md` 用三个 checkbox 表达决策：`- [ ] 采纳` / `- [ ] 合并到 [[目标节点]]` / `- [ ] 丢弃`；同页正文附证据卡链接、候选父路径、`summary_hint`。

回灌命令只处理「恰好勾了一项」的页；勾零项 = 未决策、勾多项 = 冲突并跳过；处理后把该页移到 `04-待整理/_已处理/`。采纳 → 追加 `origin: user` 节点到结构化数据并重建索引；合并 → 把这些卡的挂载改到目标节点。

### 工作台四页与静态生成

工作台是**脚本生成的静态 Markdown 清单**，不是动态查询（Dataview/Bases 的查询结果不落盘，AI 与检索读不到，与「库是 SSOT」冲突，明确不装）。

- `待修标题-方法卡.md`：仅列标题可疑的 `method` 卡（实测 245 条），每行 `- [ ] [[卡文件]] · 现标题 → 建议：xxx`；
- `待修标题-例题卡.md`：规则改不动的残余（规则命中率低的）；
- `待审提议.md`：提议索引，每行 `- [ ] [[提议-id]] · 候选父路径 · 证据卡 N 张`；
- `空壳节点.md`：无卡、无笔记、非噪声的骨架节点（**940 个**）按章分组；
- `README.md`：三件事各怎么做 + 回灌命令。

每个数字都是当前实测值，刷新即重算。

### 工作台回灌（勾选即生效）

回灌命令**只认 `- [x]`**；写回前逐个备份受影响文件到 `.backup/<时间戳>/`；方法卡行解析格式 `[[卡文件]] · 现标题 → 建议：新标题`，采纳 `→` 之后的文本写入 `title` 并清 `title_suspect`，同时触发文件重命名；例题卡页则按「规则重写」语义处理。

### 规则重写（retitle）

`retitle --rule-only` 可重复执行，只作用于 `title_suspect = true` 的卡：

- `example`（1858 张，其中 1042 张可疑）：`{章}·{题型}（例N）`，从 `chapter + topic + 例号` 生成；实测标题全部因「长度 > 24 字」被判可疑，规则化后即可落回阈值内。
- `map / symptom / pitfall`（68 / 29 / 3 张）：直接用 `topic`，必要时截断。
- `method`：**不做规则重写**（见下条）。

### 方法卡人工修标题

`method` 卡 417 张中 245 张标题可疑，剩余 172 张已可读（≤24 字）——**只修可疑的 245 张，不动已可读的 172 张**。

这 245 张是引用可信度的核心（AI 会把标题当方法名念出来），走「人工 + 建议」：工作台给出建议标题（由 `topic + method_chain 首项` 生成，agent 可批量补建议），使用者只表态采纳或改写。

### 章名别名表

新增 `chapter_alias` 配置（一张两列表：讲义章名 → KK 章节名列表，一对多），供挂载算法把「同章范围」按别名展开。

- 根因：KK 的章是**细粒度书**（`导数定义与计算`、`导数与几何应用`、`常数项级数`、`幂级数`、`特征值与特征向量`、`二次型`），讲义章是**粗粒度模块**（`一元函数微分学`、`无穷级数`、`相似理论`），所以双向包含匹配会失败，现有脚本退到「同科目全库」兜底。
- 影响面：914 张卡（`example` 724 / `method` 176 / `map` 10 / `symptom` 3 / `pitfall` 1）。
- 落地后重跑挂载，并对 `anchor_score` 与覆盖率**双指标**报告；别名表不进 vault（是仓库侧配置），但要被体检输出引用。

### 回灌：vault → 结构化数据

`reindex --from-vault` 反向解析 `考研数学/` 下的 Markdown，重建 `nodes.jsonl` 与 `cards_anchored.jsonl` 并刷新检索索引（BM25 与图）。

- 解析范围只有 `考研数学/` 前缀；`03-笔记/`、`04-待整理/` 按各自规则处理；
- 卡片按 frontmatter `id` 对齐；`title` 变化触发重命名；`doc_type` 按目录推断（`02-证据卡/` → card，`03-笔记/` → note）；
- 用户节点从 MOC 的 heading + `^user-` 锚点（或 frontmatter 列表）解析回 `origin: user`；
- 手写笔记挂载：`03-笔记/*.md` 的 frontmatter `anchors: ["[[章#节点]]"]`，与卡同等参与检索，但出处只到文件（不得出现页码）。

### OCR 接线与降级

只 OCR 张宇 **18 讲 309 页 + 9 讲 97 页 = 406 页**，产出落到 `build/ocr/`（不进 git）；1000 题试题册 195 页走文本层抽取，解析册 568 页不做。

- 工具链：MinerU `--tier basic --source modelscope`（ONNX、CPU、离线）→ 失败退 `rapidocr-onnxruntime`（模型内置于 wheel）→ 再失败则该批标 `ocr_degraded`。
- 降级判定：公式行覆盖率 < 60% → 该批只进 `raw`，不生成方法链/公式字段，MOC 上标注 `ocr_degraded`。
- 张宇内容一律 `doc_type: card`、出处 `文件名 + 页码区间`，**不带** `bbox`。

### 张宇卡合流与挂载

OCR 结果按现有卡 schema 归一后写进 `02-证据卡/`（增量、不覆盖），再跑挂载：能挂上骨架的挂上，挂不上的进提议。验收要求「新增卡 100% 有挂载 或 进提议」，不留无归属内容。

### 依赖与插件

- Python 3.13 单语言；已有 `jieba`、`rank_bm25`；本 PRD 新增 `pytest`（快速回路）；**不装** fastapi / torch（检索服务是 M5）。
- Obsidian 插件只两个：`Omnisearch`（中文全文搜索）、`Obsidian Git`（库内提交与回滚）；均为可选，缺省时退化为命令行 grep 与 git。不装 Dataview / Bases。

## 测试决策

测试基线沿用 ADR-0003 第 10 项：pytest 分层，默认回路 `pytest -m "not smoke"`；不建 CI，质量门禁是一条本地命令（pytest 快速回路 + 体检脚本）。当前仓库**没有**测试目录，本 PRD 是测试基线的起点。

### 导出 seam：vault 目录树

**最高层级接缝**：不 import 内部函数，只跑导出到临时目录，然后断言**目录树与文件内容**。覆盖：目录结构齐全、每章一个 MOC、卡文件数与挂载卡数一致、卡 frontmatter 字段完整、节点 heading 层级与 `path` 一致、`exercise_hint` 噪声节点不出现、mermaid 代码块存在、工作台四页生成且数字与输入数据一致。

### 幂等与 --force 备份

同一份输入连续导出两次，第二次**不产生任何 diff**（含 mtime 与内容）；`--force` 前必须生成 `.backup/<时间戳>/` 且备份文件数与将被覆盖文件数一致；未加 `--force` 时对已存在文件一律跳过（改一个标题后重跑，手改内容仍在）。

### 回灌 seam：vault → 结构化数据

给定临时 vault：改一张卡的 `title`、在 MOC 里加一个 `origin: user` 节点、勾选一条提议、写一篇带 `anchors` 的笔记 → 跑回灌 → 断言结构化数据与索引反映了这四处变化，且体检输出的对应数字同步变化。这是 SSOT 方向的唯一证据，必须覆盖而不是只测导出。

### 工作台 seam：清单页 ⇄ 回灌

断言清单行格式可解析、`- [ ]` 项一律不生效、`- [x]` 项生效且写前备份存在、`→` 之后的文本成为新标题、勾多项的提议页被跳过并计入冲突数。

### 体检 seam：数字门禁

体检脚本输出 JSON 作为断言面：`title_suspect`、`cards_no_anchor`、`fallback_global`（兜底挂载数）、`origin_user_nodes`、`empty_nodes`、`ocr_degraded`、`alias_miss`。这些都是**可观测业务数字**，适合做门禁，不测内部实现。

### OCR seam：接线与阈值判定

只测接线与降级判定，不测 OCR 质量本身：用 3 页样例或固定文本替代真实推理，断言产出落点正确、覆盖率计算正确、低于阈值时该批被标 `ocr_degraded` 且只写 `raw`、`build/ocr/` 不进 git。

### 写入安全 seam：前缀外零改动

在临时库中预置一篇「C++ 笔记」，跑全流程（导出 / 回灌 / 工作台 / 提议落地），断言该文件与库根其它文件零改动；同时断言所有写入都落在 `考研数学/` 前缀内。

### 测试先例

仓库现有 `check_kb.py` 的 JSON 输出是可复用的「数据侧门禁」先例（数字断言而非字符串比对）；`anchor_cards.py` 的 `--min` / 覆盖率统计是参数化门禁的先例。两者都保留，并入 pytest 回路。

## 范围外

- **检索服务（M5）**：`bge-m3` 整卡嵌入、三路召回、RRF 融合、`127.0.0.1:8765` 常驻服务、文件监听自动增量。ADR-0002 决策 3/4/5/6 暂缓而非推翻，等 M1–M4 交付后单独拍板。
- **Canvas / Excalidraw 双向编辑**：视图只读，为什么不做见 ADR-0004 第 5 条。

### 与 ADR-0004 的两处偏差（需回写 ADR）

1. **提议门槛放宽到 example 卡簇**：ADR-0004 第 4 条只允许对 `method` 卡提议，理由是 `example` 卡应走挂载。但实测可读的 `method` 候选只有 46 张，达不到 M3「≥40 个用户节点」的验收线（需 87% 采纳率）。因此本 PRD 增加第二类候选：同章同题型 ≥3 张的 `example` 卡簇 → 提议一个题型级节点。落地后应把这一条增补进 ADR-0004。
2. **「586 张挂不上」这个前提已过时**：ADR-0004 引用的 586 张来自旧的挂载口径；当前数据的真实问题是「914 张章名对不上却仍被兜底挂上」。修法是章名别名表（本 PRD 新增决策），而不是把它们都变成用户节点。

### 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| OCR 质量不达标（公式错行） | 张宇方法卡不可用 | 覆盖率 <60% 即降级只进 `raw`；MinerU 失败退 rapidocr；再不行 M4 部分交付 |
| 别名表维护成本 | 新增讲义时章名对不上会悄悄回退到兜底 | `alias_miss`（兜底数）进体检门禁，不为零就报警 |
| 增量策略的副作用 | 抽取算法改进后旧卡标题不会自动修好 | 明确写进文档；修标题本来就是人工动作，属同一循环 |
| mermaid 大章卡顿 | 打开 MOC 变慢 | >150 节点只画 `depth ≤ 3`；全树走 markmap 页 |
| 提议误报 | 用户节点被垃圾提议污染 | 只对可读标题的卡提议；一页一决策；误报率抽检 ≤20% |
| 文件重命名 | 双链与 git 历史碎片化 | 按 id 匹配、脚本负责改名；`Obsidian Git` 可在库内回滚 |

### 开放问题

1. **发布阻塞**：本机 `gh` 已安装但 token 失效（HTTP 401），PRD 暂时只能以仓库内 Markdown 形式存在；恢复 `gh auth login` 后应发成 GitHub Issue 并打 `ready-for-agent`。
2. **M3 验收的构成**：`≥40 个用户节点` 拆成「提议采纳 ≥15 + 手工新增其余」。若别名表落地后候选骤减，手工新增就得承担主要份额——这是否可接受，需要在使用两周后回看。
3. **章名别名表的作者**：初版由脚本对 `alias_miss` 的章名做最近邻建议、人工确认；表本身是否进 git、是否要版本化，待 M3 落地时定。
4. **`.backup/` 的保留策略**：目前只规定「重建前备份」，没有规定保留几份、多久清理；库越来越大时需要一条清理规则。
5. **M2 的 `<400` 依赖规则覆盖全量例题卡**：若规则只能覆盖一部分（例如 `topic` 为空的卡），实际残余会高于预估，需在 M2 首轮实测后调整验收线。
