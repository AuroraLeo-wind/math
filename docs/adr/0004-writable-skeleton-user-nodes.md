# ADR-0004：骨架可增——用户节点与提议机制

- 状态：已接受
- 日期：2026-11-06
- 关联：ADR-0001（骨架算法）、ADR-0002（vault 为 SSOT）

## 背景

ADR-0001 把 KK 导图重建为 1748 个原生节点、2375 张卡挂载其上（覆盖 75%）。但用户的需求是「形成自己总结与导图思想匹配的新结点插入导图中」——他要在 KK 的分类法上长出自己的分类，而不只是给 KK 补脚注。ADR-0002 的代价清单里已写明「Markdown 成为 SSOT 后，导出脚本不能覆盖手改内容」，但没回答「新节点从哪来、归谁管」。

## 决策

1. **骨架可增**：原生节点与用户节点在同一棵树里共存，用户节点带 `origin: user` 与其挂靠的父路径。
2. **用户节点必须有一行 `summary`（≤40 字）**：这是它区别于原生节点（只有名字）的唯一补偿，也是检索判断"该节点管什么"的依据；长结论仍落成证据卡，不写进节点。
3. **用户节点没有位置坐标**：它不在任何 KK 原图上，因此不带 `bbox`，视图渲染时用虚线框与原生节点区分。
4. **新节点只能由「提议 → 人采纳」产生，不自动生成**：脚本对挂不上骨架的卡做聚类（同父路径 + 方法名相近），只对 `kind=method` 且标题可读（中文字符占比 ≥60%）的卡发起提议；提议写进工作台，人勾选后才成为用户节点。
5. **视图是派生物，永远只读**：图从骨架渲染，不能在图上直接改结构；在画布里加一个框不等于骨架加一个节点。

## 被否决的备选

- **骨架纯只读**：等于承认"你的总结只能写成卡"，与需求直接冲突。
- **全自动建节点**：OCR 噪声会造出「力在造心邻域内」这类垃圾节点，且它们会污染节点 BM25 与视图；而人工从 586 条候选里逐条录入不现实，所以折中是"机器提议、人决策"。
- **用户节点存独立目录，只在视图上连线**：会形成两套真相（树里没有它、检索看不到它），与"SSOT 是 Markdown、命中要给骨架路径"冲突。

## 后果

- 骨架从"KK 的重建物"变成"混合树"，重建时必须按 `origin` 区分处理，增量导出不得覆盖用户节点。
- `summary` 若写成空话，用户节点会退化为噪声；工作台里对空泛 summary 要能在巡检中暴露出来。
- 提议质量决定 M3 的成败：只对可读标题的 `method` 卡提议，是为了把候选从 586 压到 80–150，代价是 `example` 卡永远不会催生新节点（它们走挂载）。
